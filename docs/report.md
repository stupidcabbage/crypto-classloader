# Собственный загрузчик классов

## результаты jmh

| Загрузчик         | Загрузок/с | Погрешность, 99,9% |
| ----------------- | ---------- | ------------------ |
| URLClassLoader    | 19831.267  | ± 1573.833         |
| CryptoClassLoader | 33971.960  | ± 2301.851         |

Оба загружают `SecretGreeting`, каждый вызов создаёт новый загрузчик.
Измеряются создание загрузчика и загрузка без инициализации, включая
дешифрование и закрытие `URLClassLoader`. Подготовка файлов вынесена в `@Setup`.
Тут крч разница составила ~ 1,71 раза. Все числа можно глянуть в файле: jmh-results.json.

## почему родитель не может загрузить `SecretGreeting`, а `CryptoClassLoader` - может

потому что `SecretGreeting` собран отдельно в `labs` и отсутствует на classpath приложения.
Очевидно, что родитель его не находит, а `CryptoClassLoader` читает зашифрованный файл
из своего каталога и восстанавливает байты:

на схеме вот так:

```text
findClass: a.b.C → root/a/b/C.class → чтение → XOR → defineClass
```

## что такое делегирование родителю в `loadClass` и почему `findClass` вызывается последним

делегирование - это процесс, когда загрузчик сначала спрашивает родителя есть ли нужный класс.
если есть - берёт его, если нет, вызывает `findClass` и загружает сам.
на схеме вот так:

```text
loadClass: кэш → родитель → findClass
```

родителя спрашивают первым, чтобы использовать общие классы. так например,
`GreetingProvider` должен быть один для всех загрузчиков, иначе объекты
не получится привести к этому интерфейсу.

## почему два загрузчика из одинаковых байтов дали два разных класса, и где у типа «сидит» определивший загрузчик

```text
одинаковые байты → загрузчик 1 → Class 1
                → загрузчик 2 → Class 2
```

хоть байты и одинаковые, тип в JVM задаётся парой: { бинарное имя, определивший загрузчик }.
загрузчики разные - типы тоже разные. поэтому `c1 == c2` и
`c1.isInstance(экземпляр c2)` дают `false`.
ссылка на загрузчик хранится в объекте `Class`, получить её можно через `getClassLoader()`.
если класс определил родитель, там будет ссылка на родителя.

## зачем общий `GreetingProvider`

чтобы обе копии пейлоада использовали один и тот же интерфейс из загрузчика приложения.
тогда оба объекта можно привести к `GreetingProvider` и вызвать `greeting()`.
если каждый загрузчик определит свой интерфейс, имя будет одинаковым, но типы разными.
при приведении к интерфейсу приложения получим `ClassCastException`.

## как ведёт себя собственный пейлоад во втором загрузчике

```text
загрузчик 1 → CountingGreeting: вызовы №1, №2
загрузчик 2 → CountingGreeting: вызовы №1, №2 (два объекта)
```

у `SecretGreeting` строка не меняется, а `CountingGreeting` при каждом вызове
увеличивает статический счётчик. у второго загрузчика своя копия класса,
поэтому его счётчик тоже начинается с 1. но два объекта этого загрузчика
делят одно поле и получают номера 1 и 2.

статический блок срабатывает один раз для каждой копии класса, новые объекты
его не запускают заново. повторный `loadClass` возвращает тот же `Class`.

## где это может пригодиться и что может сломаться

например, для плагинов, разных версий библиотек, генерации классов на лету
или загрузки зашифрованного кода. общий API можно оставить у родителя,
а реализации загрузить отдельно.

из проблем - одинаковые имена классов ещё не означают одинаковые типы,
поэтому можно получить `ClassCastException`. ещё могут не найтись зависимости,
а при отладке придётся разбираться, какой загрузчик что загрузил.
XOR здесь только скрывает сигнатуру файла: ключ есть в программе,
а восстановленные байты получает JVM, так что защиты кода тут нет.

## дополнительные опыты

```text
parent-first: кэш → родитель → локальный файл
child-first:  кэш → локальный файл → родитель
```

в child-first сначала проверяется локальный файл, а если его нет, запрос идёт к родителю.
такой порядок включён только для выбранных классов, `java.*` всегда делегируется.
если `SecretGreeting` есть у родителя, parent-first берёт его класс,
а child-first определяет свою копию.

зависимости пейлоада ищет определивший его загрузчик. `GreetingText` он загружает сам,
а за `GreetingProvider` обращается к родителю.

```text
запрос класса: файл отсутствует / не читается → ClassNotFoundException
неверный XOR-ключ                           → ClassFormatError
вызов greeting() без GreetingText           → NoClassDefFoundError
                                             причина: ClassNotFoundException
```

без `GreetingText` сам объект создаётся, но при вызове `greeting()` получаем ошибку,
потому что JVM понадобился отсутствующий класс. вывод всех опытов: run-output.txt.
